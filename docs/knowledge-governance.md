# Knowledge curation, releases and evaluation

The catalog has two different assurance questions: whether a rule behaves as
implemented, and whether independent reviewers agree that it models real threats
accurately. These are reported separately. No human approvals or production
accuracy results were generated by this implementation.

## What changed

- Twelve existing rules now receive source-specific curation, not generic filler.
  Eight existing deterministic rules gained seven-state regression fixtures each.
  Four retrieval-only rules remain hypotheses rather than becoming detectors.
- Releases are immutable, content-addressed snapshots with an atomic active
  pointer, explicit approval, expiring exceptions, revocation and rollback history.
- Audit output classifies each remaining gap by rule, workstream and next action.
  Missing tests remain untested; missing mappings remain visible.
- Reviewed-holdout intake checks the source evidence, label review, architecture
  families, training overlap and declared coverage before accepting evaluation.

## Bounded legacy curation

`backend/app/knowledge_base/curation.py` binds each overlay to the SHA-256 digest
of the original rule. If that source rule changes, the overlay is not applied and
the loader reports a stale-curation issue. Re-check the changed rule before
updating the digest. Existing rule files and their predicates are not rewritten.

| Area | Existing rules improved | Primary sources checked on 2026-10-04 |
| --- | --- | --- |
| AWS storage and keys | `AWS-S3-001`, `AWS-KMS-001` | [S3 Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html), [KMS key policies](https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html) |
| AWS delegated roles and key deletion | `ENT-CLOUD-EXTERNAL-ID`, `ENT-CLOUD-KEY-DELETE` | [Third-party external IDs](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_common-scenarios_third-party.html), [KMS deletion](https://docs.aws.amazon.com/kms/latest/developerguide/deleting-keys.html) |
| SaaS tenant isolation | `ENT-SAAS-CACHE`, `ENT-SAAS-JOBS` | [OWASP multi-tenant security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html) |

Each overlay adds a versioned source description, scoped counterexamples and a
verification procedure. Source checks are engineering work, not independent
approval. Existing explicit framework mappings are retained, not expanded. For
the eight control rules, category-only fallback mappings are suppressed rather
than presented as exact mappings. Other legacy gaps remain in the audit.

The regression cases are positive, protected, unknown, conflicting, planned,
partial and wrong scope. A positive fixture proves that the predicate matches
the submitted control state; it does not prove that a deployed system is vulnerable.

## Release workflow

Run these commands from the project root. Choose a protected local path for the
SQLite release ledger; it is deliberately not created inside the source catalog.

```powershell
node scripts/run-backend-python.mjs scripts/audit_knowledge.py --contracts
node scripts/run-backend-python.mjs scripts/audit_knowledge.py --strict
node scripts/run-backend-python.mjs scripts/knowledge_releases.py --database data/kb-releases.sqlite stage --actor alice
node scripts/run-backend-python.mjs scripts/knowledge_releases.py --database data/kb-releases.sqlite assess <content-digest>
```

`stage` does not publish. It snapshots the normalized rules, resolved mappings,
framework registry and source diagnostics. It never changes catalog JSON files.
`assess` computes a reproducible assessment digest including runtime regression
results and evaluator source hashes. Timing measurements do not affect the digest.

An authorized reviewer must inspect the actual assessment. The author cannot
approve their own release. Example approval and activation:

```powershell
node scripts/run-backend-python.mjs scripts/knowledge_releases.py --database data/kb-releases.sqlite approve <content-digest> --reviewer bob --reason "Reviewed change record SEC-123" --assessment-digest <assessment-digest> --valid-until 2026-12-01T00:00:00Z --waivers approved-exceptions.json
node scripts/run-backend-python.mjs scripts/knowledge_releases.py --database data/kb-releases.sqlite publish <content-digest> --approval-id 1 --actor alice --reason "SEC-123 rollout" --expected-revision 0
```

Use real reviewer identities and decisions, not these example values. The local
CLI records operator attestations; it does not authenticate those identities.

An exception is a narrow record such as:

```json
[
  {
    "rule_id": "EXISTING-RULE-ID",
    "code": "missing_counterexamples",
    "reason": "Named owner will complete the documented legacy review",
    "tracking_reference": "SEC-123",
    "expires_at": "2026-12-01T00:00:00Z"
  }
]
```

An exception must match a real waivable gap in that assessment. Empty catalogs,
loader errors, quarantined source records, broken fixtures, unresolved framework
identifiers and failed regression tests cannot be waived. Rule removals need an
explicit exception as well. Exceptions do not erase gaps or create rule approvals.
The bundled legacy catalog will not satisfy strict publication until its actual
gaps are fixed or an authorized reviewer explicitly accepts allowed exceptions.

Rollback selects a previously published immutable artifact. First assess and
approve it against the **current** active baseline, then use `rollback` with that
approval ID and active revision. A previous approval cannot authorize new removals
or a changed baseline. Stale clients cannot overwrite another activation.

`active`, `history` and `export <digest>` expose pointer state, transition history
and the portable snapshot. Records cannot be overwritten through the store API;
SQLite triggers also reject accidental update/delete of artifacts and history.
A database owner can still alter the database. Use filesystem access controls,
backups and an external audit sink for enterprise retention requirements.

## Parent API integration contract

Import `KnowledgeReleaseStore`, `ReleaseConflict` and `ReleaseGateError` from
`app.knowledge_base.releases`. No API routers or shared requirements are changed
by this module.

| Function | Behavior |
| --- | --- |
| `stage(kb, actor=...)` | Returns immutable artifact digest and payload; no activation. |
| `assess(digest, baseline_digest=...)` | Returns governance gaps, changes, regression coverage, blockers and assessment digest. |
| `approve(...)` | Requires distinct reviewer, exact assessment digest, expiry and explicit exceptions. |
| `publish(...)` / `rollback(...)` | Recheck gates, approval and baseline under compare-and-swap; return changed rule IDs and reassessment requirement. |
| `revoke_approval(id, actor=..., reason=...)` | Prevents subsequent activation using that approval; does not silently switch an already active catalog. |
| `load_active()` | Returns a validated `ThreatKnowledgeBase` using the exact snapshot, without re-normalizing current framework mappings. |
| `reassessment_plan(before, after, reports)` | Conservatively identifies affected saved reports; does not mutate or rerun them. |

Bind actor/reviewer to the authenticated server principal, never request-supplied
identity strings. Restrict mutations to authorized administrators and reviewers.
Map `ReleaseConflict` to HTTP 409 and `ReleaseGateError.blockers` to a structured
validation response. Snapshot loading must come from the store, not arbitrary
client-supplied canonical rules. Keep the running KB replacement and retrieval
index refresh coordinated using the returned content digest.

Include `kb.release_provenance` in analysis/report provenance. For selective
reassessment, saved report records should contain `id` and `knowledge_provenance`
with `content_digest` plus `evaluated_rule_ids`. Absent provenance forces review;
new rules also require reassessment because old findings cannot prove their scope.
Set `AEGIS_KB_RELEASE_DB` to opt in at startup. `get_knowledge_base()` and
`reload_knowledge_base()` then require an existing database, a published snapshot,
valid content digest and non-expired, non-revoked approval and exceptions. There
is no fallback to the bundled catalog if this configured store fails validation.
Without the setting, the existing bundled-catalog behavior is retained.

Publication returns `restart_required: true` and `runtime_applied: false`. Restart
the backend to replace shared analysis engines and retrieval indexes safely;
publishing never hot-swaps their references. The parent API should show the
requested digest separately from the loaded `release_provenance.content_digest`.
A running analysis retains its already-loaded snapshot; expired or revoked review
blocks the next load/restart. Reassess and approve the same digest against the
current baseline to renew it, then publish a new activation revision.

The parent router exposes `POST /enterprise/knowledge/releases/{digest}/reassessment`
to installation administrators only. Its input accepts `baseline_digest` and either
up to 100 `report_ids`, or `after_report_id` with a `limit` of 1-100. With no explicit
baseline it uses the active release. It reads provenance from immutable
`assessment_results`, not browser workspace data or caller-supplied reports.
Unknown legacy provenance requires review; a report already generated with the
target release is not needlessly flagged. Results include a continuation cursor,
bounded change lists and counts. This operation does not rerun or edit assessments.

API errors are 401/403 for authentication/installation access, 400 for invalid
release operations, 404 for missing releases/reports/approvals, 409 for stale
assessments or activation revisions, 422 for schema or governance gate failures,
and 503 for unavailable storage. Request identity fields cannot substitute for
the authenticated reviewer. Status compares activation revision as well as digest
so renewal of an approval still indicates when workers need restarting.

## Reviewed holdout intake

`app.knowledge_base.holdout.HoldoutScenario` defines the input contract. A scenario
contains its query and supporting document text, author, source reference, domain,
architecture family, expected findings and assessed STRIDE categories. Each label
needs named affected components, severity, rationale and a quote that actually
exists in its referenced source. Empty expected findings require an explanation.

An independent label reviewer calls `record_review(record, reviewer=..., reason=...)`
only after checking those labels. The attestation is tied to the full source and
label content. Editing either invalidates it. Partial labels cannot measure recall.
The intake never accepts `rule_generated` data as a human-authored holdout.

```powershell
node scripts/run-backend-python.mjs scripts/validate_holdout.py reviewed-corpus.json --training actual-training-inventory.json
```

The default gate requires 100 distinct architecture families, all six STRIDE
categories assessed, and coverage across web, identity, AWS, Azure, GCP, Kubernetes,
SaaS, payments, AI, agents and MCP. Duplicate scenarios and overlap with training
or validation query/family inventory fail the gate. Supply the real inventory;
an absent inventory cannot establish independence. Reduced thresholds used by
unit tests are included explicitly in the report and are not production acceptance.

Optional `--predictions` and `--judgments` score a completed run. Predictions must
cover every scenario, including empty finding lists. A human adjudicator supplies
one-to-one expected/predicted matches and a review bound to `judgment_digest`.
Unmatched labels count as false negatives and unmatched predictions as false
positives. The report provides precision, recall and confidence intervals; it
does not silently match finding titles or award accuracy for missing runs.

Passing intake is not an accuracy result. Even a scored run describes only its
reviewed corpus. Reviewer authenticity, corpus representativeness, correctness of
labels and complete training lineage still need organizational validation.
