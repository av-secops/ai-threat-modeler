# Aegis Threat 2.3.2

Updated 4 October 2026. This refresh includes the application, tests and operating
guides. Earlier release tags are retained.

## Products and assessment

- Organize models by product, release and application. A release can contain a
  complete-product model and several application models without overwriting them.
- Save drafts and report revisions with optimistic conflict handling, clear Back
  navigation, application scope and creation dates.
- Use an adaptive, versioned questionnaire before generating a numbered DFD.
  Unknown answers remain visible; shared-control answers can be reviewed together.
- Review uploaded diagrams against their source, correct components, flows and
  trust boundaries, and inspect source evidence before analysis.
- View product and portfolio dashboards with severity, review status and coverage
  filters. Counts use the latest saved report per model rather than every rerun.
- Compare explicit saved revisions side by side, review identity mappings and
  retain immutable comparison snapshots and decisions. A disappeared finding is
  not automatically a verified fix.

## Analysis and knowledge

- Correlate prompt, document, questionnaire and IaC evidence by component and
  deployment scope. Prefer explicitly named subjects over broad rule matches.
- Preserve unknown, planned, conflicting and partial controls. A WAF is not proof
  of safe query construction or application authorization.
- Retain documented weaknesses without inventing absent boolean properties;
  include internal LLM prompt-injection review candidates without treating
  ambiguous statements as confirmed component-level weaknesses.
- Separate inferred attack-path hypotheses from stated connectivity and expose
  identity, authorization and exploit prerequisites on each path.
- Include remediation acceptance criteria and required verification evidence in
  finding details and reports. These are proposed checks, not tests run by Aegis.
- Validate rule contracts and provenance, curate existing cloud/SaaS/payment/AI
  rules, and support immutable KB releases with separate author/reviewer approval,
  publication, rollback and reassessment. Activating a KB release requires a worker
  restart; publication does not silently hot-swap running engines.
- Add reviewed-holdout intake, bounded persistent retrieval metrics and more
  efficient evidence indexing and comparison matching.

## Access and integrations

- Verify OIDC bearer identities and explicit product grants. Background jobs
  recheck current server-configured grants before analysis and result publication.
- Require product-admin approval for acceptance, verified fixes and false-positive
  decisions. Acceptance needs an owner and expiry; closure needs structured,
  passing verification records. Expired acceptance becomes pending review without
  rewriting its historical decision.
- Provide versioned organization patterns and an opt-in, retryable Jira outbox
  for existing issues. Ticket status alone does not close a risk.
- Add model-as-code validation/comparison gates and offline, pinned-schema OTM and
  Threat Dragon interchange with conversion-loss warnings.
- Provide read-only AWS EC2/RDS/Lambda/S3 discovery and offline snapshot comparison.
  Live collection is explicit and optional; normal analysis does not contact AWS.

## Updating

Back up `backend/data/workspaces.sqlite3` before updating. Stop the app first or
use SQLite's online backup API. Keep your `.env`, local models and workspace data
outside the release source tree.

```powershell
.\start.ps1 -Stop
.\start.ps1 -InstallDependencies
```

For manual setup, run `pip install -r requirements.txt` in your virtual environment
and `npm ci`. Python 3.12 is recommended; the frontend needs Node 22.13+ or a newer
even-numbered LTS line. Optional AWS discovery uses
`backend/requirements-cloud.txt`; optional adapter training uses
`backend/requirements-training.txt`.

The base manifest includes JWT verification, JSON Schema validation and the HTTP
dependencies used by the new APIs. SQLite and the job queue still use Python's
standard library. The local STRIDE classifier pickle is a regenerable cache and
is no longer shipped. Temporary plans, competitive notes and validation diaries
have been removed; setup, usage, security, testing and release guides remain.

## Scope and remaining work

This is an assisted technical review tool, not a security sign-off engine.
Confirmed means supported by submitted evidence, not verified on a deployment.
STRIDE assessment counts do not prove complete threat coverage.

- Independent accuracy evaluation and remaining legacy KB curation are open.
- OIDC bearer verification is implemented; browser PKCE login and SCIM are not.
  Legacy unscoped tokens retain installation-wide access. Configure explicit
  product grants before shared use.
- Pattern, Jira, interchange and cloud APIs do not yet have complete browser
  management workflows. Jira issue creation, persisted cloud snapshots and
  Azure/GCP discovery are not included.
- Shared review uses version conflicts, not simultaneous live diagram editing.
- SQLite stores source text and is not encrypted by the application. Protect and
  back it up; production identity, cloud and ticket integrations need acceptance
  testing in your own environment.

See [workspace access](../workspace-access.md), [knowledge governance](../knowledge-governance.md),
[security workflows](../security-workflows.md) and [model as code](../model-as-code.md)
for configuration and exact boundaries.
